# AZDO → GitLab Migration Checklist (v2)

Source: Azure DevOps Server 2022 (on-prem) · Target: GitLab.com Premium/Ultimate · one AZDO project at a time.

**Tags:** **[A]** collected automatically by `azdo-analyzer` · **[S]** flagged by the tool, a person confirms · **[M]** manual.
Items marked *(new)* were added to the original checklist. The per-repo dossiers generated by `azdo-analyzer analyze` are this checklist, pre-filled.

## How to keep the analysis simple

- **Automate discovery.** `azdo-analyzer inventory --all` pulls the inventory from the REST API into one workbook (one row per repo). The original list of endpoints:
  - `_apis/git/repositories`
  - `_apis/build/definitions`
  - `_apis/release/definitions`
  - `_apis/distributedtask/variablegroups`
  - `_apis/serviceendpoint/endpoints`

  The tool also reads: task catalog and task groups, policies, run history and timelines, deployments, environments, checks, deployment groups, secure files, agents and their capabilities, extensions, feeds and service hooks.
- **Export classic definitions as JSON.** The raw cache keeps every definition (`out/raw/<project>/build_definition|release_definition/*.json`). Task groups are expanded inline.
- **Classify into archetypes.** Stack × build tool × deploy target × artifact (Archetypes sheet, plus pipeline "fingerprints" that find clones). Most orgs end up with 5–8.
- **Map each archetype to a shared GitLab CI template.** Only repos that don't fit an archetype need custom analysis.
- **Score complexity per repo.** Baseline: YAML pipeline = Low, Classic = Medium, Classic release with approvals and multiple stages = High. `rules/scoring.yaml` adds weighted points on top. Migrate Low first to prove the pattern.
- *(new)* **Drop dead weight first.** Disabled, draft, never-run and dormant definitions and repos are listed as retire candidates.

## 1. Project level

- [ ] [S] Project name, owner team, business criticality *(name automatic; owner and criticality manual)*
- [ ] [A] Number of repos, build pipelines and release pipelines, each linked to the repo/project that uses it *(Tracker + Dependencies sheets)*
- [ ] [A] Active vs dormant (last commit date, last pipeline run, last deployment)
- [ ] [A] *(new)* TFVC in use (TFVC repo or recent changesets). Blocks a plain git push; needs git-tfs conversion
- [ ] [A] *(new)* Retire candidates: disabled, draft, never-run or dormant definitions; repos with no commits in N days
- [ ] [A] *(new)* Orphans: pipelines whose repo is deleted or disabled; repos with no pipeline
- [ ] [A] *(new)* Installed extensions (marketplace and private), the source of custom tasks
- [ ] [S] *(new)* Other assets in use: wiki, boards, test plans, feeds, so nothing is forgotten
- [ ] [M] *(new)* Migration wave, business sign-off, freeze window

## 2. Repositories

- [ ] [A] Repo name, size, LFS usage
- [ ] [A] Default branch and branching model (GitFlow, trunk, `release/*`)
- [ ] [A] Branch policies: required reviewers, min approvers, build validation, linked work items, comment resolution *(each mapped to its GitLab equivalent)*
- [ ] [A] Path-based reviewers → GitLab `CODEOWNERS`
- [ ] [A] Tags and versioning convention
- [ ] [A] Submodules or cross-repo references
- [ ] [A] Open PRs at cutover (close/merge first; they don't migrate cleanly)
- [ ] [M] Repo permissions; who has push/bypass rights
- [ ] [A] Hardcoded AZDO URLs in code, scripts, README badges, `nuget.config` / `.npmrc` / `settings.xml`
- [ ] [A] *(new)* Disabled repos and forks; branch/tag counts; stale branches (clean up before pushing)
- [ ] [A] *(new)* Size against the GitLab.com **10 GB per-project** limit
- [ ] [A] *(new)* Merge-type policy (squash, rebase, semi-linear) → GitLab merge method / squash setting
- [ ] [A] *(new)* Reset votes on push, creator self-approval → "remove approvals on push", "prevent author approval"
- [ ] [A] *(new)* Status-check policies → external status checks (**Ultimate only**)
- [ ] [A] *(new)* File-size / path-length / reserved-name / author-email policies → push rules
- [ ] [S] *(new)* PR templates → `.gitlab/merge_request_templates/`; `AB#123` links → Jira/GitLab issue references
- [ ] [A] *(new)* GitLab path slug for each repo and slug collisions (spaces and special characters in names)

## 3. Build pipelines

- [ ] [A] YAML or Classic
- [ ] [A] Triggers: CI branches, path filters, PR triggers, scheduled, pipeline-completion triggers
- [ ] [A] Agent pool: Microsoft-hosted vs self-hosted; OS (Windows matters for .NET Framework)
- [ ] [S] Toolchain versions: JDK, Maven, Node, Python, .NET SDK/MSBuild, Ant *(from task inputs, agent capabilities, project files)*
- [ ] [A] Tasks used: all of them listed; marketplace/custom tasks flagged where they need an equivalent
- [ ] [A] YAML templates / `extends` from other repos
- [ ] [A] Build number format and versioning logic (GitVersion, counter expressions, etc.)
- [ ] [A] Tests: framework, result publishing, code coverage format
- [ ] [A] Quality gates: SonarQube, SAST/DAST, dependency scanning, license checks
- [ ] [A] Artifacts produced: type, name, retention
- [ ] [A] Caching in use
- [ ] [A] Matrix / parallel jobs
- [ ] [A] Average duration (baseline for GitLab runners)
- [ ] [A] *(new)* **Settings outside the YAML file**: UI-defined variables and UI trigger overrides on YAML pipelines
- [ ] [A] *(new)* Classic task groups, expanded recursively (with the version used)
- [ ] [A] *(new)* Logging commands in scripts (`##vso[task.setvariable]`, `build.updatebuildnumber`, `artifact.upload`)
- [ ] [A] *(new)* AZDO predefined variables in scripts (`$(Build.SourcesDirectory)`, `BUILD_BUILDID`) → `$CI_*`
- [ ] [A] *(new)* `System.AccessToken` usage → `CI_JOB_TOKEN` / project access token
- [ ] [A] *(new)* Output variables, runtime parameters / queue-time variables → `spec:inputs`; conditions/`dependsOn` → `rules`/`needs`
- [ ] [A] *(new)* Container jobs and service containers; multi-repo checkout, submodules, `fetchDepth`, clean options
- [ ] [A] *(new)* Demands → runner tags; timeouts / retries / `continueOnError` → `timeout` / `retry` / `allow_failure`
- [ ] [A] *(new)* Test result format: TRX/NUnit must be converted to JUnit
- [ ] [A] *(new)* Pipeline-completion triggers: **direction flips** in GitLab (upstream triggers downstream; subscriptions only fire on tags)
- [ ] [A] *(new)* Schedules → GitLab pipeline schedules (UI/API, not YAML)
- [ ] [A] *(new)* Run stats: success rate, p95 duration, queue time, trigger mix, branches actually built, peak concurrency

## 4. Release pipelines

- [ ] [A] Classic release or YAML multi-stage with environments
- [ ] [A] Stages/environments (dev → QA → UAT → prod) → GitLab environments
- [ ] [A] Artifact source: which build, which branch filter
- [ ] [A] Release triggers: continuous deployment, scheduled, manual
- [ ] [A] Pre-/post-deployment approvals and approvers → protected environments + deployment approvals
- [ ] [A] Gates: work item query, REST API check, Azure Monitor, etc.
- [ ] [A] Deployment groups / target VMs → runner or SSH/agent strategy
- [ ] [A] Deploy method: `kubectl`/`oc`, Helm, scripts, IIS/WinRM, Ansible, ARM/Terraform
- [ ] [A] Environment-specific variables and config transforms
- [ ] [M] Rollback / redeploy process
- [ ] [S] Release naming and audit/evidence requirements (compliance) *(naming automatic; evidence manual)*
- [ ] [A] *(new)* Artifact default-version rules and aliases (`$(System.DefaultWorkingDirectory)/_alias/drop` paths in scripts)
- [ ] [A] *(new)* Stage trigger conditions (after stage, manual, partially succeeded) → `needs` + `when: manual`
- [ ] [A] *(new)* Deployment queue settings (parallel, sequential, latest only) → `resource_group` / process mode
- [ ] [A] *(new)* Stage-scoped variables → environment-scoped CI/CD variables; process parameters
- [ ] [A] *(new)* Agentless jobs: manual intervention, delay, REST calls → `when: manual`, `when: delayed`, curl jobs
- [ ] [A] *(new)* Which stages actually deploy (deployment history); don't migrate stages that never run
- [ ] [A] *(new)* Checks on YAML environments (approvals, branch control, business hours, exclusive lock, required template)
- [ ] [A] *(new)* Approver users and groups that must exist in GitLab before cutover

## 5. Variables, secrets and connections

- [ ] [A] Pipeline variables: secret vs plain, settable at queue time
- [ ] [A] Variable groups and which pipelines share them → group-level CI/CD variables
- [ ] [A] Key Vault-linked variable groups → Vault / external secrets approach
- [ ] [A] Secure files (certs, keystores, provisioning profiles)
- [ ] [A] Service connections: Kubernetes/OpenShift, Docker registry, Artifactory, Azure, SonarQube, SSH: what each authenticates to
- [ ] [M] Service account / token owners and expiry dates
- [ ] [A] *(new)* Variable names invalid as GitLab keys (dots, hyphens) → proposed keys; plain-text values with secret-looking names
- [ ] [M] *(new)* Secret values can't be exported: record owners / source of truth for re-entry; check GitLab masking rules
- [ ] [A] *(new)* Auth scheme of each connection → replacement (OIDC `id_tokens`, GitLab agent for Kubernetes, masked/File variables)
- [ ] [A] *(new)* Real usage of connections (execution history, pipeline authorizations); drop unused ones
- [ ] [A] *(new)* Resources shared across projects → parent GitLab group variables
- [ ] [A] *(new)* Agent capabilities per pool (OS, SDKs, tools) = what runner images need

## 6. Artifacts and feeds

- [ ] [A] Azure Artifacts feeds in use (Maven, npm, NuGet, PyPI, Universal)
- [ ] [A] Upstream sources and views (`@release`, `@prerelease`)
- [ ] [A] Consumers of those feeds (what breaks if the feed moves) *(feed URLs in repo config files)*
- [ ] [M] Target: Artifactory or GitLab package registry
- [ ] [M] Snapshot vs release repo mapping
- [ ] [A] *(new)* Container registries pushed to; base-image registries (`FROM`)
- [ ] [A] *(new)* Cross-pipeline artifact downloads → `needs:project` (Premium) or package registry

## 7. Dependencies and integrations

- [ ] [A] Downstream pipelines triggered by this one / upstream ones that trigger it
- [ ] [A] Webhooks and service hooks (Teams, Slack, Jira, ServiceNow)
- [ ] [M] Notifications and email subscriptions
- [ ] [M] Dashboards or reports built on AZDO data
- [ ] [A] *(new)* Hard-coded AZDO REST calls in scripts/tools
- [ ] [A] *(new)* Shared template repos → GitLab CI/CD components / `include:project`

## 8. Identity and access *(new)*

- [ ] [S] AZDO groups/teams → GitLab group roles; Entra ID SAML SSO + SCIM on the GitLab.com group; user email mapping
- [ ] [S] Who can bypass branch policies or approve releases
- [ ] [M] Segregation of duties and evidence retention

## 9. Network and runners *(new: on-prem source, SaaS target)*

- [ ] [A] Internal-only deploy targets and services (deployment groups, private hosts in service connections): need **self-managed runners inside the network** or the GitLab agent for Kubernetes
- [ ] [M] Firewall egress from runners to GitLab.com, inbound webhooks, internal CA on runners
- [ ] [A] Peak concurrency and build minutes per pool, for runner sizing

## 10. Cutover and validation *(new)*

- [ ] [M] Push repos from inside the network (GitLab.com usually can't reach the on-prem server); sync during the parallel run
- [ ] [M] Parallel run on the same commit: compare artifacts, test counts, durations
- [ ] [M] AZDO repos read-only, pipelines disabled; badges, links, webhooks and feed consumers updated
- [ ] [M] Rollback plan and sign-off

**Tip:** run `azdo-analyzer inventory --all` for wave planning, then `azdo-analyzer analyze --project "<name>"` before each wave. Manual effort concentrates on the `[M]` items, classic release approvals, and secrets.
